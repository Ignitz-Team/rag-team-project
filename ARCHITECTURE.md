# How Life Lens AI Works

This document explains how the app actually works end-to-end: the pieces, the
data flow, and where to look in the code for each part. For setup/run
instructions, see [README.md](README.md).

## 1. What the app does

Life Lens AI lets a user upload "memories" (documents, notes, photos, links)
into a personal timeline, then ask questions about them in a chat interface.
Chat answers are generated by an LLM (Groq) and, when relevant, grounded in
the user's own uploaded content via retrieval-augmented generation (RAG) —
this is the core feature the "RAG" in the project name refers to.

## 2. Tech stack at a glance

| Concern | Technology | Where |
|---|---|---|
| App framework | Next.js 16 (App Router) | `src/app/` |
| Relational data | Postgres (hosted on Supabase) | `src/lib/db.js` |
| Vector search | pgvector extension on the same Postgres DB | `src/lib/vectorStore.js` |
| Embeddings | Local ONNX model via `@xenova/transformers` (`all-MiniLM-L6-v2`, 384-dim) | `src/lib/embeddings.js` |
| LLM generation | Groq (OpenAI-compatible chat completions API) | `src/lib/groqService.js` |
| Auth | Custom email/password + Google (Firebase client SDK), signed session cookie | `src/lib/session.js`, `src/middleware.js` |
| Chat formatting | `react-markdown` | `src/app/chat/page.js` |

There is deliberately **no separate vector database service** — vectors live
in the same Postgres database as everything else, via the `pgvector`
extension. This was a deliberate simplification after an earlier standalone
ChromaDB setup proved unreliable to run locally (see git history).

## 3. Request-level architecture

```
Browser
  │
  ▼
src/middleware.js   ── runs on EVERY request first
  │  - public paths (/, /login, /register, /api/auth/*, /api/users) pass through
  │  - everything else requires a valid `session` cookie, else:
  │      • page routes  → redirect to /login?redirect=<path>
  │      • API routes   → 401 JSON
  ▼
src/app/**/page.js (UI)  or  src/app/api/**/route.js (API)
  │
  ├─→ src/lib/db.js          (Postgres: memories, users, otps, memory_chunks)
  ├─→ src/lib/vectorStore.js (pgvector reads/writes on memory_chunks)
  ├─→ src/lib/embeddings.js  (local embedding generation)
  ├─→ src/lib/groqService.js (LLM calls to Groq)
  └─→ src/lib/session.js     (sign/verify the auth cookie)
```

Every page under `src/app/` (except `/`, `/login`, `/register`) is
protected — the middleware is the single gatekeeper, so individual pages
don't need to re-check auth themselves.

## 4. Authentication & sessions

The source of truth for "is this user logged in" is a signed, `httpOnly`
JWT cookie named `session` (see `src/lib/session.js`, uses the `jose`
library, HS256, 7-day expiry, secret from `SESSION_SECRET`).

**Email/password login** (`src/app/login/page.js` → `POST /api/auth/login`
in `src/app/api/auth/login/route.js`):
1. Look up the user by email in the Postgres `users` table.
2. Compare the password against the stored bcrypt hash.
3. On success, sign a session JWT and set it as the `session` cookie.

**Google login** (`signInWithPopup` via Firebase client SDK) never touches
`/api/auth/login` — it authenticates with Firebase directly in the browser.
Afterward, the client calls `POST /api/auth/session`
(`src/app/api/auth/session/route.js`) with the Firebase-confirmed
name/email, which mints the same kind of session cookie. This keeps both
login paths ending in the same place: a valid `session` cookie the
middleware can check. Note there's no Firebase Admin SDK verifying the
Google identity server-side — the app trusts what the Firebase client SDK
already confirmed.

**Registration** (`src/app/register/page.js`) is a 2-step flow entirely on
our own backend, not Firebase:
1. `POST /api/auth/send-otp` — checks the email isn't already registered,
   generates a 6-digit OTP, stores a bcrypt hash of it in the `otps` table,
   and emails it (`src/lib/otpService.js`, via Nodemailer). SMS delivery via
   Twilio was never configured for this project — the code path exists
   commented-out in `otpService.js` but isn't used.
2. `POST /api/auth/verify-otp` — checks the OTP against the stored hash and
   expiry.
3. `POST /api/users` — creates the actual `users` row (bcrypt-hashed
   password). The user then logs in normally.

**Logout** (`POST /api/auth/logout`) just clears the cookie. Both the
sidebar and profile page call this before clearing `localStorage` and
redirecting to `/login`.

Separately from the session cookie, the UI also keeps a few display-only
values in `localStorage` (`userName`, `userEmail`, `userPhoto`, etc.) purely
for rendering greetings/avatars without a round-trip — these are **not**
what gates access; the cookie is.

## 5. Data model (Postgres)

Set up by `src/lib/db.js`'s `ensureTables()` (called lazily by API routes)
and `scripts/init-db.js` (`npm run db:init`):

- **`users`** — `id, name, email (unique), phone, password (bcrypt hash)`.
- **`otps`** — pending registration OTPs (`email, phone, otp_hash, expires_at`).
- **`memories`** — every uploaded item: `title, description, category, date,
  year, file_name, file_type, preview (base64 data URL), text_content, url,
  deleted, deleted_at, file_size`. Deletes are soft (`deleted = true`).
- **`memory_chunks`** — the RAG index: `id, memory_id (FK → memories),
  chunk_index, source_file, text, embedding VECTOR(384)`, with an HNSW
  cosine-distance index for fast nearest-neighbor search.

## 6. Ingestion pipeline (upload → searchable)

Entry point: `POST /api/memories` in `src/app/api/memories/route.js`.

1. **Text extraction.** The upload page (`src/app/upload/page.js`) reads
   text-like files (`.txt/.csv/.json/.md`) client-side via `FileReader`.
   PDFs are *not* extracted client-side — instead the API route extracts
   text server-side using `pdfjs-dist` from the base64 preview. Images get
   no text extraction at all (stored, but never indexed for search).
2. **Persist the row.** The memory is inserted into `memories` (Postgres) —
   this happens regardless of whether indexing succeeds, so the item is
   never lost even if the next steps fail.
3. **Chunk.** `chunkText()` splits the extracted text into ~800-character
   chunks with 120-character overlap.
4. **Embed.** Each chunk is embedded locally via
   `src/lib/embeddings.js` (Xenova `all-MiniLM-L6-v2`, no external API call,
   no cost, runs fully offline once the model is cached).
5. **Store.** `saveDocumentWithEmbeddings()` in `src/lib/vectorStore.js`
   batch-inserts the chunks + embeddings into `memory_chunks`, tagged with
   `memory_id` and `source_file` metadata.
6. **Report back.** The API response includes an `indexing: {indexed,
   chunkCount, reason}` field. If indexing failed (e.g. no text, DB error),
   the upload UI shows an inline warning — the memory is still saved, it's
   just not searchable in chat yet.

`PATCH`/`DELETE` on `/api/memories` keep the index in sync: editing
`text_content` re-chunks/re-embeds/re-indexes; deleting removes the memory's
chunks from `memory_chunks` too.

## 7. RAG retrieval & chat flow

Entry point: `POST /api/ai/query` in `src/app/api/ai/query/route.js`, called
from `src/app/chat/page.js`.

1. The user's question is embedded locally (same model as ingestion, so
   questions and documents live in the same vector space).
2. `queryTopK()` runs a pgvector cosine-distance query against
   `memory_chunks`, returning the K nearest chunks.
3. Matches farther than `MAX_CONTEXT_DISTANCE` (0.75) are discarded as too
   weak to be useful — this is what decides whether the answer counts as
   "grounded" or not.
4. **If there's usable context:** those chunks are passed to Groq
   (`src/lib/groqService.js`) with a system prompt telling it to prioritize
   the supplied context.
   **If not:** Groq is called with a plain general-knowledge system prompt
   instead — the chat still answers, just without pretending to know your
   documents.
5. The response includes `usedContext` (boolean) and `sources` (matched
   file names). The chat UI renders a small badge under each AI reply:
   **📄 From your documents** (with source file names) or **💬 General
   knowledge (not from your documents)** — this is the fastest way to
   visually confirm whether ingestion/retrieval actually worked for a given
   question.
6. AI replies are rendered through `react-markdown` so formatted answers
   (bold, lists, code) display properly instead of as raw text.

## 8. Everything else in the UI

- **Dashboard** (`src/app/dashboard/page.js`) — memory count, recent
  activity feed, and a local (browser-notification-based) reminders
  feature stored in `localStorage`.
- **Timeline** (`src/app/timeline/page.js`) — chronological view of all
  memories with edit/delete.
- **Search** (`src/app/search/page.js`) — client-side filter/search over
  loaded memories, with its own recent-searches history in `localStorage`.
- **Summary** (`src/app/summary/page.js`, `src/app/summary/[year]/page.js`)
  — memories grouped and drilled into by year.
- **Uploads history** (`src/app/uploads/page.jsx`) — full upload log
  including soft-deleted items, distinct from the "Upload" page which is
  for adding new memories.
- **Profile & settings** (`src/app/profile/page.js` and
  `personal-info`/`security`/`privacy-settings`/`notification-settings`/
  `storage-usage`/`help-support`/`about-app`) — account management,
  including a real "Delete Account" flow that removes the Firebase account
  (if any) and wipes local app data, and a per-user profile store
  (`src/lib/userProfile.js`, keyed by email in `localStorage`) for extra
  fields like DOB/location that aren't part of the `users` table.

## 9. Environment variables

See [.env.example](.env.example) for the full list. The two worth
understanding rather than just copying:

- `DATABASE_URL` — must be Supabase's **pooled** (Supavisor, port 6543)
  connection string, not the direct one, so the app doesn't exhaust
  Postgres's connection limit.
- `SESSION_SECRET` — signs the auth cookie. Changing it invalidates every
  existing session (everyone gets logged out).

## 10. Diagnostics

- `node scripts/check-vector-store.js` — checks `DATABASE_URL` is
  reachable, the `vector` extension is installed, and reports the current
  `memory_chunks` row count. The first thing to run if chat answers never
  show the "From your documents" badge.
- `[INGEST]` and `[vectorStore]`-tagged `console.log` lines throughout the
  ingestion path narrate exactly where a given upload succeeded or
  stopped.
